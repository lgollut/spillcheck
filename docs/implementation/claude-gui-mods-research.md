# Claude GUI Mods as a candidate passive route

Researched October 9, 2026. Initial research and static validation installed no mod or changed user configuration. The later separately authorized owned local experiment is recorded below. This is engineering research, not phase-0 acceptance. The observed GUI producer is 2.1.293; its exact runtime declarations and side-chat dispatch remain unmeasured.

## Availability and installation

Anthropic documents Mods in the terminal and the Desktop Code tab, with Desktop support from embedded Claude Code 2.1.286 and terminal support from 2.1.287. The observed 2.1.293 producer is therefore within the documented availability range. This version comparison does not establish that the current session permits or loaded a mod. Mods are plugin-contained functions, distinct from the settings-file command hooks already measured. [Official Mods overview](https://code.claude.com/docs/en/plugins/mods/overview#turn-mods-on-or-off)

Installed plugins can be enabled at user, project, or local scope. Local scope records the enablement in `.claude/settings.local.json`; project scope affects `.claude/settings.json`, and user scope affects the user's settings. Desktop local sessions share this configuration with the terminal. After a shell installation or update, `/reload-plugins` loads it in an open session. A future owned experiment should use a disposable project and remove only its own plugin enablement and installation records. This remains a proposed experiment; no installation was performed. [Official plugin installation and scopes](https://code.claude.com/docs/en/plugins/install#choose-an-install-scope), [Mods installation and reloading](https://code.claude.com/docs/en/plugins/mods/overview#install-or-update-a-mod)

Static `claude plugin validate <directory>` reports events and API calls without running the mod or starting a session. The troubleshooting guide also describes `claude plugin test` from a directory without a module as a no-install availability diagnostic. Settings, managed policy, and remotely served rollout state can still disable Mods. The static check was subsequently measured below; the availability diagnostic and actual load remain unmeasured. [Static validation](https://code.claude.com/docs/en/plugins/mods/create#check-what-claude-code-reads-from-your-mod), [Availability diagnostics and refusal reasons](https://code.claude.com/docs/en/plugins/mods/troubleshoot#check-whether-mods-can-load)

## Passive events worth measuring

The documented observation pattern is to call `next(e)` with the unchanged event. For streaming `turn.step`, an async generator forwards the stream and returns its completed result unchanged. No prompt rewriting, approval override, command replacement, new model call, session message, or UI output is necessary for collection research. [Official event guide](https://code.claude.com/docs/en/plugins/mods/events#follow-a-turn)

| Candidate event | Documented useful data | Unmet side-chat question |
| --- | --- | --- |
| `prompt.submit` | Submitted text before the turn | Does the side composer dispatch it, and does it identify that side conversation? |
| `command.run` filtered to `btw` | Command arguments and origin | Does this GUI entry point dispatch it, and can its submission be tied to the resulting side turn? |
| `turn.start` | Prompt text and turn identity | Does an internal side loop raise it? |
| `turn.step` | Turn, request index, optional agent identity, streamed response | Does the side loop dispatch it with a stable native identity? |
| `turn.complete` | Final answer, turn identity, optional agent identity and completion state | Can the side final be tied to its prompt without text or timestamp inference? |

The prompt and turn events are documented, but the event guide does not promise that Desktop side chats dispatch them. They are candidates for a genuine GUI probe. `classic.SubagentStop` wraps the same settings-hook contract and does not by itself fix the focused run's absent callback. [Prompt and turn events](https://code.claude.com/docs/en/plugins/mods/events#rewrite-or-add-to-a-prompt), [Command events](https://code.claude.com/docs/en/plugins/mods/reference#commands-and-configuration), [Classic events](https://code.claude.com/docs/en/plugins/mods/events#handle-the-settings-hook-events)

## Exact-version and identity limits

The current reference describes the API as of 2.1.290 and warns that online declarations can be older than the installed engine. Exact declarations are generated when a mod directory is loaded or reloaded; those files take precedence over the web pages. Generating them would require a later authorized load, so this research did not do it. [Versioned reference](https://code.claude.com/docs/en/plugins/mods/reference), [Per-version declarations](https://code.claude.com/docs/en/plugins/mods/create#get-type-definitions-for-your-version)

The inspected official declaration file is pinned at commit `684800b206824dfd0cc8a876e8604b20f72c3617` and identifies its writer as 2.1.277. In that earlier contract, `$.session.id()` returns the transcript's session ID. `turnId` correlates start, step, and completion; a step has an index and optional `agentId`. Subagent runs do not raise `turn.start`. Stream text has a block index; its opaque `ref` is limited to that step. `$.session.messages()` supplies role/text/tool summaries without native row UUIDs or an ordinary message handle. These declarations therefore provide a candidate session and loop correlation, not a proved side-prompt identity, persistence guarantee, or mapping to existing native transcript rows. [Official pinned declarations](https://github.com/anthropics/claude-code/blob/684800b206824dfd0cc8a876e8604b20f72c3617/mods/types/claude-code.d.ts)

The exact 2.1.293 declarations, a main-to-side affiliation field, and identity stability across duplicate delivery, restart, and host overlap remain gates. Matching the side text, its display appearance, or its timestamp would not satisfy them. This is an inference from the documented identity limits and Spillcheck's existing canonical-source requirements, not a provider guarantee that those fields are absent from 2.1.293.

## Proposed probe boundary

If a later genuine experiment is authorized, first validate a tiny observer module and confirm it loads in the same official GUI session. Limit it to the selected native session, one controlled side question, and bounded event counts and bytes. Record marker presence and keyed equality of upstream identities without printing names, text, paths, or IDs. Forward every event and response chunk unchanged, and fail open when the diagnostic observer cannot deliver.

The Mods API supports process calls with an argument vector and stdin. That gives a possible transport to the existing owned helper and encrypted queue without putting source text in command arguments, a file archive, a mod key-value store, telemetry, or UI logs. Exact 2.1.293 support must be measured before using it. No new raw archive or export is proposed. [Official file/process/network API](https://code.claude.com/docs/en/plugins/mods/api#reach-files-processes-and-the-network)

A diagnostic event reaching an encrypted queue proves delivery, not canonical analysis. Production adoption still requires genuine prompt and final coverage, a stable side identity, duplicate suppression, signed ingestion, bounded failure handling, and explicit unavailable-history accounting. The GUI feature remains disabled until those phase-0 contracts pass. A Mods probe can narrow the missing capability; current documentation does not establish completion.

## Prepared candidate and static result

The [candidate probe](../../Tests/ClaudeGUIModProbe/README.md) now exists. Its unprepared template observes nothing. A private disposable copy gates every observation on the exact selected native session before reading event content. Its journal accepts only controlled marker labels, field-presence counts, and keyed comparisons, with 256 rows and one MiB bounds. Original events, streamed chunks, and completed results pass through unchanged. No provider text is archived or delivered for analysis.

The actual embedded executable independently reported 2.1.293 and passed strict static validation of both the plugin and its owned local marketplace. It recognized all seven registered event kinds and only `$.session.id` and `$.process.run` API calls. Constructed checks passed for refusal before accessing unrelated event fields, identity hashes, unchanged responses, observer failure, provider errors, private file boundaries, and journal limits. Validation used an isolated config that was removed. It was not installed at static-validation time; the later trial and removal are recorded below. [Redacted static result](claude-gui-mod-static-validation-2026-10-09.json)

The validator labels `prompt.submit` and `command.run` as gating hooks without `.catch`. This probe returns `next(e)` and catches its diagnostic errors. The official failure contract skips an uncaught observer before `next`, or preserves an already returned downstream result without running it twice. No fail-closed handler was added. This documented behavior still needs exact-runtime acceptance if the GUI load is authorized. [Official hook failure behavior](https://code.claude.com/docs/en/plugins/mods/events#handle-a-hook-that-fails)

The documented GUI path uses the plugin browser and local-only enablement. A local marketplace necessarily adds its own user-settings declaration, so local enablement does not make every installation write project-local. The review instructions therefore call for an absent, uniquely owned marketplace identity, current unowned-settings comparison, exact plugin uninstall, and exact owned-marketplace removal. [Official marketplace lifecycle](https://code.claude.com/docs/en/plugins/create-marketplace#remove-the-marketplace-to-start-over)

The [separately authorized manual trial](claude-gui-mod-harness-compatibility-2026-10-09.json) verified absent owned identities, preserved unowned settings in five bounded known settings/registry files, and installed only at local scope in the disposable GUI project. It verified the exact local project installation record and no user or shared-project enablement. Initial snapshots stayed only in the installer process memory during a bounded wait. The user then confirmed both the main and side prompts and visible responses.

The journal contained only one selected-session `session.start` callback, 580 bytes, with no main or side marker. Read-only inspection of the exact original parent positively found the main control prompt in a user row and the final marker in an assistant row, both with matching native session identity and producer 2.1.293. This is a failed main-content positive control, so it cannot establish that the side APIs omit the side conversation. The startup callback has no host, PID, surface, or event-native identity fields, and cannot retrospectively be attributed to the GUI rather than the installer. The cached owned module retained the expected scope and seven literal event kinds. No exact generated declarations or owned runtime diagnostic log was available. No provider turns, GUI automation, or broad provider logs were used for this diagnosis.

Exact local uninstall and owned marketplace removal both exited successfully. All five current unowned settings/registry comparisons passed across removal, and the owned entries were absent afterward. The existing marketplace registry differed between the initial and final snapshots during the manual interval; user, local, project, and plugin settings remained equal. Those initial snapshots were only in the ended process memory, so the registry difference is not localized or attributed. The helper did not restore an old file. The user confirmed plugin reloading after removal. Before deleting the private probe and exact owned cache, the cleanup rechecked absent owned registry/settings entries and verified cached code and scope exactly matched the private prepared plugin. Both directories were removed; no broader cache or raw archive was touched. Runtime unloading was operator-confirmed rather than directly instrumented. Working GUI main dispatch, side prompt/final coverage, native side affiliation, stable identities, and signed ingestion remain gates.
