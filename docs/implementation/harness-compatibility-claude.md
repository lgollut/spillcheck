## Implemented Claude behavior

Claude collection and owned hook setup now use the shared compatibility decision. An unfamiliar release can use a recognized native contract without receiving validation from an older acceptance run. The recorded executable version, each transcript row's producer version, and host evidence remain separate. A missing row version becomes `unknown`. Changing version metadata alone preserves native identity and content revision. GUI collection stays disabled until its required source contracts pass phase 0.

The parser checks native session and row identity, timestamps, message roles, complete JSONL records, tool-result correlation, and required field types. Missing or changed required fields produce controlled gaps. A conflicting tool result does not stop readable prompts or responses from collecting. Unknown content blocks remain visible as omissions while supported sibling blocks are analyzed. Extra envelope fields are tolerated; unknown top-level record kinds remain explicit gaps unless their omission is already supported by the recognized contract.

Recognized tool-result payloads include additional string fields. Existing text pointers and UTF-8 ranges remain stable. Newly present strings change the content revision and retain their own source pointers. Conflicting results for one native tool-use identity in a bounded page remain ambiguous and are omitted rather than merged.

An empty initial hook read retries through the existing bounded durable queue. It cannot establish completion or use hook text as a second authority. Replay of an already analyzed nonempty transcript remains stable. Hook display IDs do not become native transcript identities.

The cursor now records parser contract `claude-transcript-5`. Contract 4 followed the measured CLI and GUI metadata corrections below, but it also treated every `attachment` row as metadata because attachment payloads sit under `attachment`, not top-level `message` or `content`. Prompts typed while a turn was running exist only as `queued_command` attachments, so contract 4 dropped them without a gap. Contract 5 collects them as user prompts, recognizes listed harness-context subtypes without content, and keeps other attachment subtypes as unsupported-content gaps; the runs below used contract 4 or earlier. A missing or older contract invalidates the completion shortcut and permits a bounded reread of an unchanged source. Existing document IDs, native source identities, checkpoints, and processed-source receipts remain usable. Recovery references identify the exact encrypted row location. A full recognized reparse with no row gaps can resolve that omission; readable sibling content alone cannot.

The CLI acceptance runner records the executable it actually invoked, its version before and after the run, and the producer versions actually parsed. `--expected-version` is an assertion for a particular acceptance run. The production eligibility decision does not depend on that assertion. The acceptance executable also has a disposable `configureHook` mode using production owned-hook setup. The signed-app runner uses that mode, an explicitly scoped native store, and the signed bundle's helper. It waits for storage and collection readiness before launching the provider.

## Signed-app startup failure

The signed-app runner configured a disposable owned production hook, but the app reported `key-unavailable-queue--25308` with `storageReady=false` and `collectionConfigured=false`. It did not launch a Claude provider process. No native content, signed child scanning, replay, or restart behavior was measured in this attempt.

The app exited normally through the acceptance finish sentinel. Owned hook removal, disposable provider authentication removal, and owned process shutdown passed. `cleanupPending=true` records that the scoped encrypted vault and guarded cleanup manifest remain for later cleanup. Encrypted marker inspection and vault cleanup did not pass. This failure must not be counted as signed ingestion or connection verification evidence.

A single immediate retry used the final r2 signed build, actual Claude executable 2.1.295, and the rebuilt configuration acceptance executable. Its required assertions included at least two committed native child occurrences covering `userPrompt` and `finalResponse`. Startup again returned `key-unavailable-queue--25308`, before those assertions could be exercised. The retry launched no provider, observed no native content, and performed no replay. It exited normally, removed its owned registration and temporary authentication, and retained its own exact guarded vault with `cleanupPending=true`. The retry report records `signedNativeChildCommitEstablished=false`. These failed reports remain historical evidence; later signed startup passed without establishing the cause of the intermittent Keychain error.
