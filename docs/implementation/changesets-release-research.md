# Changesets and GitHub Actions research

Checked on 2026-10-09. This note records the release-tool behavior behind the CI plan. It does not implement workflows.

Changesets supports applications and non-npm projects through a private `package.json` containing `name` and `version`. For Spillcheck, use one root package named `spillcheck`, with `private: true`, and keep the Swift build unchanged. Explicitly set `.changeset/config.json` to `privatePackages: { "version": true, "tag": false }`. Changesets v3 defaults both properties to false. The plan's separate tag job owns tagging, so the CLI's private-tag option can stay disabled. [Beyond npm](https://changesets.dev/guide/beyond-npm), [configuration reference](https://changesets.dev/guide/config#privatepackages)

The current published CLI is 3.0.3, and the current released GitHub Action is 2.1.2. CLI v3 accepts Node 24, and the action itself uses the Node 24 runtime. Action v2 rejects CLI v2. Pin an immutable released action commit, `ae32849d5ba541f9ae29e40e22a623bc13562f51` for 2.1.2, and lock the CLI dependency. The official examples use `@v2`, but GitHub's tag-ref API returned 404 for that major alias during this research. [CLI manifest](https://github.com/changesets/changesets/blob/main/packages/cli/package.json), [action 2.1.2 release](https://github.com/changesets/action/releases/tag/v2.1.2), [compatibility implementation](https://github.com/changesets/action/blob/v2.1.2/src/utils.ts)

## Versioning and one accumulated release PR

The root `changesets/action` supports `version-script`, `github-token`, `pr-title`, and `commit-message`. It has no `private-version` or `private-tag` inputs. Configure private behavior in the Changesets config. The separate `/version` subaction calls its custom command input `script`. [Released root action inputs](https://github.com/changesets/action/blob/v2.1.2/action.yml), [version subaction inputs](https://github.com/changesets/action/blob/v2.1.2/version/action.yml)

With no `publish-script`, the root action creates or refreshes a version PR when a nonempty changeset exists, and does nothing after that PR merges. It does not create tags. Use a custom `version-script` to run Changesets and synchronize the application's version metadata and root lockfile. Explicitly set `create-github-releases: false` and `push-git-tags: false` to document that another job owns them. [Root action control flow](https://github.com/changesets/action/blob/v2.1.2/src/index.ts), [version command implementation](https://github.com/changesets/changesets/blob/main/packages/cli/src/commands/version/index.ts)

The action uses the fixed branch `changeset-release/main`, finds an open PR for that head/base pair, and updates it. Each run resets the generated branch to the triggering main SHA before recomputing versions and changelog from main's pending changesets. Manual changes to that generated branch can disappear on the next refresh. Contributors should edit their changeset on the feature branch, or submit a correction on main. [PR implementation](https://github.com/changesets/action/blob/v2.1.2/src/run.ts), [branch reset implementation](https://github.com/changesets/action/blob/v2.1.2/src/github.ts)

For one package, accumulated changesets select the highest requested bump. Two patch changesets produce one patch release; patch plus minor produces one minor release. They do not increment the version once per feature. Every contributing changeset remains in the release plan for changelog generation. [Release-plan implementation](https://github.com/changesets/changesets/blob/main/packages/assemble-release-plan/src/flatten-releases.ts)

The generated PR body still uses npm publishing language, even in version-only mode. If a custom app-specific description matters, update the body after the action using its `pr-number` output. [Generated PR body](https://github.com/changesets/action/blob/v2.1.2/src/run.ts)

## Changeset validation

`changeset status --since <base-ref>` checks the PR's changesets against its base. Plain `changeset status` can accept a pending changeset inherited from main, so it is unsuitable for enforcing a new feature's release note. Fetch history and use the actual PR head plus its base ref; GitHub's ordinary PR checkout otherwise points at a synthetic merge commit. [Status command](https://changesets.dev/guide/cli#status), [changeset filtering](https://github.com/changesets/changesets/blob/main/packages/read/src/index.ts), [PR event SHA](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#pull_request)

The official status check exits successfully when no versionable packages changed, and accepts empty changesets. If the requirement is that every ordinary PR adds a changeset, make the required gate explicitly find newly added `.changeset/*.md` files in the PR diff. Parse them, ignore the Changesets README, and validate the package name, semver bump, and nonempty explanation for release changes. This stricter check is a project policy beyond the CLI's status behavior. [Blocking validation guide](https://changesets.dev/guide/automating#blocking), [status implementation](https://github.com/changesets/changesets/blob/main/packages/cli/src/commands/status/index.ts)

The user chose explicit empty changesets for docs, tests, and CI work. `changeset add --empty` supports that. Add a short reason to explain why no release is needed. Empty changesets do not bump the version. CLI `version` removes them along with the release changesets, but the root action does nothing when every pending changeset is empty. Such files remain on main until the next nonempty release consumes them. Calling the `/version` subaction without checking for nonempty release changesets can instead create a cleanup-only PR; it has no guard of its own. [CLI empty changesets](https://changesets.dev/guide/cli#empty-changesets), [root action guard](https://github.com/changesets/action/blob/v2.1.2/src/index.ts), [CLI consumption](https://github.com/changesets/changesets/blob/main/packages/apply-release-plan/src/index.ts), [version subaction implementation](https://github.com/changesets/action/blob/v2.1.2/src/version/index.ts)

The release PR deletes consumed changesets, so exempt it from adding a new one. Limit the exemption to the expected same-repository branch and release bot identity. Replace that check with validation of the generated version, changelog, allowed changed files, and consumed changesets. Require the release branch to be up to date with main before merging. This is the project policy needed to prevent an older generated PR from releasing code whose changesets have not yet been included. The official guide also exempts its generated release branch. [Automation guide](https://changesets.dev/guide/automating#non-blocking)

## Credentials and workflow events

GitHub currently treats PRs created or updated using `GITHUB_TOKEN` differently from ordinary push events. Their `opened`, `synchronize`, and `reopened` workflow runs require manual approval. Pushes and tag events made with that token still do not start workflows. Use a GitHub App installation token for the release-branch writes and tag creation so release PR tests and `push.tags` release automation run automatically. A PAT is an alternative. [Current GITHUB_TOKEN behavior](https://docs.github.com/en/actions/concepts/security/github_token)

Give the App repository `Contents: write` and `Pull requests: write`, install it only on this repository, and request those permissions explicitly when generating a token. Store its private key as a secret and its client ID as a variable. `actions/create-github-app-token` defaults to the current repository when owner/repository inputs are omitted. Its token is revoked at job completion, so generate one in each job that needs it. Pass it through the Changesets `github-token` input; the root action does not accept a different `GITHUB_TOKEN` environment value. [App-token action](https://github.com/actions/create-github-app-token), [Changesets token handling](https://github.com/changesets/action/blob/v2.1.2/src/index.ts)

The Changesets documentation calls for enabling Actions' repository setting allowing creation and approval of PRs. Use ordinary `pull_request` with read-only permissions for tests and required validation. Keep App credentials on trusted main jobs. [Changesets prerequisites](https://changesets.dev/guide/automating#prerequisites)

## Tag timing and concurrency

Use a separate tag job after tests pass for the exact main SHA that merged the release. Detect a real version increase rather than an absence of changesets. A later feature merge may already have added new changesets before release automation runs. Check that the commit belongs to the generated release PR, the changelog contains the version, and an existing `vX.Y.Z` tag either points to that same commit or causes a hard failure. Never move a release tag. These are project design recommendations. Changesets' own single-package git-tag convention is `vX.Y.Z`; npm's `--tag` option controls an npm distribution label and is unrelated. [CLI tag and npm-tag reference](https://changesets.dev/guide/cli#git-tag)

Serialize release-PR refreshes in their own concurrency group and skip tested snapshots that are no longer main's current head. Keep tag creation outside that group. GitHub's default concurrency allows one running and one pending run, replacing older pending runs; `cancel-in-progress: false` alone does not preserve every release merge. Avoid workflow-wide coalescing or cancellation on main when the workflow owns tagging. If a serialized job must process every event, use the current `queue: max` option, which allows up to 100 pending runs. [Concurrency reference](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#concurrency)

The initial release pipeline should trigger on pushed `v*` tags, verify tag/version/changelog consistency, and publish a GitHub Release containing that version's changelog. The user chose no application assets initially. Signing, notarization, and distributable assets stay behind the existing release checks. GitHub supports tag-filtered push workflows. [Push tag events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#running-your-workflow-only-when-a-push-of-specific-tags-occurs)
